# tinytown_tool の評価：オンデバイスモデルが扱える指示の複雑さ

`tinytown_tool.py`（オンデバイスモデルと tinytowngen の Tool を組み合わせたもの）で、モデルがどこまで複雑な指示をこなせるかを 5 段階のレベルで調べた記録です。

- 評価日: 2026-10-16（第 1 回、第 2 回）
- 環境: macOS 27.0.1 / apple_fm_sdk 0.2.1 / オンデバイスモデル（`SystemLanguageModel`、既定の設定）
- tinytowngen: commit `1ecc60155382d931dd131c8c7481cfa21e1efc36`（[notoroid/tinytowngen](https://github.com/notoroid/tinytowngen)）
- 評価スクリプト: [tinytown_eval.py](../tinytown_eval.py)

| 回 | ガイド（`LAYOUT_GUIDE`） | 試行回数 | 結果ファイル |
|---|---|---|---|
| 第 1 回 | `F` の範囲指定（`F{r,x0-x1}`）の記載なし | 各レベル 3 回 | `output/eval/results_v1.json`、画像は `output/eval/v1/` |
| 第 2 回 | `F{r,x0-x1}` を追記 | 各レベル 5 回 | `output/eval/results.json` |

## 結論

**このモデルが安定して扱えるのは、座標を指定しない、要素 2〜3 個程度の指示までです。**
座標の指定や、はみ出し・重なり・交差を考慮した配置が必要になると、tinytowngen のエラー 3 回以内に正しいレイアウトにたどり着けませんでした。

ガイドに `F` の範囲指定を書き足しても（第 2 回）、レベル 4 と 5 の結果は変わりませんでした。モデルは範囲指定を使うようになりましたが、使い方を誤るため、新しい書式エラーが増えています。
ボトルネックはガイドの記載漏れではなく、**座標と道路番号を対応づけて考える力**にあると判断しました。

## 評価の方法

### 判定のルール

tinytowngen には、配置の誤りをエラー（終了コード 1）にする仕組みがあります。たとえば、緑地を大路（F）や水路（W）が横切る場合、グリッドからはみ出す場合、要素が重なる場合です。
評価ではこのエラーの回数を数え、**3 回に達したら FAIL**（目的を達成できない）とします。4 回目以降のツール実行は、評価スクリプトが拒否します。

| 判定 | 意味 |
|---|---|
| PASS | 描画に成功し、プロンプトの要件チェックをすべて満たした |
| PARTIAL | 描画には成功したが、要件を満たしていない |
| FAIL | tinytowngen のエラーが 3 回に達した |
| NO_CALL | ツールを一度も呼ばずに応答を終えた |
| ERROR | 生成そのものが例外で失敗した |

- 要件チェックは、最後に成功した呼び出しの引数（grid、map、seed、layout）を正規表現で照合して行います。
- 試行ごとに新しいセッションを作ります。各レベルを 3 回ずつ試行しました。

### レベルと正解のレイアウト

各レベルの正解のレイアウトは、事前に tinytowngen に直接渡して描画できることを確認しています。つまり、どのレベルも解ける課題です。

| レベル | 課題 | 正解のレイアウト | 罠 |
|---|---|---|---|
| 1 | 8x5 の現代的な街を、全部商業地区で埋める | `-g 8x5 -l "C*"` | なし |
| 2 | 13x7 の平安京。中央に大路、左上に寺院 | `-g 13x7 -m heiankyo11c -l "U3{0,0} F{3} C*"` など | なし（座標は自由） |
| 3 | 10x6。左上に 2x2 の公園、縦方向の道路 5 を水路、横方向の道路 3 を大路、残りは商業 | `-g 10x6 -l "U2{0,0} W{5} F{3} C*"` | 座標と道路番号の理解（交差なし） |
| 4 | 12x8 の平安京。寺院 3 つ（{0,0} に 3x3、{10,0} に 2x2、{0,6} に 1x2）、大路を横方向の道路 2 と 5、川を縦方向の道路 6、{7,6} は工事中 | `-g 12x8 -m heiankyo11c -l "U3{0,0} U2{10,0} U1x2{0,6} F{2,3-11} F{5} W{6} B{7,6} C*"` | `F{2}` を全幅で引くと、3x3 の寺院を横切る |

実際のプロンプトの全文は、`tinytown_eval.py` の `LEVELS` に書いてあります。

## 第 1 回の考察

### 1. 交差の回避より前の段階でつまずく
レベル 4 と 5 は「交差を避ける」力を見るための課題でしたが、エラーの大半はその手前の誤りでした。

- **範囲外**：12x8 のグリッドに `U3{0,6}` を置き、下にはみ出す
- **重複**：同じ場所に `U1x2{0,0}` と `U1{0,0}` を置く
- **座標と道路番号の取り違え**：公園の x 座標 14 を、横方向の道路番号として `F{14,7}` と書く

狙っていた交差エラーまで進んだのは L5 #1 だけです。そのときも、公園の列（0〜2）を範囲から外す、という修正にはたどり着けませんでした。

### 2. エラーを読んで直す力が弱い
エラーメッセージには、正しい範囲（例：`must be 1-8`）や重なっている要素が具体的に書かれています。それでも、同じ誤りを繰り返したり（L4 #3、L5 #1）、`F{14}`→`F{13}`→`F{12}` のように的外れな修正をしたりしました。

### 3. 簡単な指示でも出力が安定しない
- レベル 1 でも、ツールを呼ばずに引数を文章で書いて終わることがありました（L1 #2）。
- エラーのあと、要件を満たさないレイアウトで満足して終えることもありました（L1 #3）。

### 4. ツールの説明に載せた例に引きずられる
レベル 2 は 3 回とも PASS でしたが、内容には次の傾向がありました。

- 寺院は 3 回とも最小の `U1` で、頼んでいない水路（`W{5}` や `W{12}`）を足していた
- 2 回は、ツールの説明にある例（`U3{0,0} U2{9,4} F{3} W{5} B{7,1} C*`）の一部（`U2{9,4}` と `W{5}`）をそのまま使っていた

要件チェックは指示された要素があるかだけを見ているので、余分な要素があっても PASS になります。

### 5. ガイドに F の範囲指定が載っていなかった
評価のあと、同じガイドだけを使う Claude Code の Skill（`.claude/skills/tinytown`）でレベル 4 を試しました。そのとき、ガイドには `W{c,y0-y1}` は載っているのに、**`F{r,x0-x1}` が載っていない**ことに気づきました。
レベル 4 と 5 は `F` の範囲指定がないと解けないので、この記載漏れが失敗の一因である可能性を確かめるため、第 2 回の評価を行いました。

なお、Claude（Skill）は、1 回目のエラーメッセージに出た `F{2,0-11}` という書式から範囲指定の書き方を推測し、2 回目（エラー 1 回）でレベル 4 に成功しています。

## 第 2 回の考察

### 1. 範囲指定は使うようになったが、正しく使えない
F の範囲指定は使われるようになりました（`F{3,0-2}`、`F{2,0-4}`、`F{2,0}` など）。ただし、使い方には次の問題がありました。

- **必要のない場面で使う**：L3 #2 では、交差がないのに範囲を区切っている
- **範囲の意味を取り違える**：L4 #5 の `F{2,0}` は、範囲ではなく単なる座標として書いている
- **書式を混ぜる**：L5 では 5 回中 4 回、`F{14,7,1}` のように「公園の座標 `{14,7}`」と「範囲」を組み合わせた、存在しない書式を書いている
- **範囲を書けない要素にまで範囲を書く**：`U1x2{0,0-2}` のように、公園にも範囲を書いている

### 2. 座標と道路番号の取り違えは変わらない
`F{10}`、`F{14,...}` のように、タイルの座標を道路番号として使う誤りは、第 1 回と同じように起きています。
エラーメッセージには `must be 1-7` と正しい範囲が書かれていますが、`F{10}` → `F{10,0-5}` → `F{8,0-6}` のように、範囲の外の番号を使い続けています。

### 3. 失敗の仕方が変わった
- レベル 4 では、エラーを出さずに、指示をほぼ無視したレイアウトで終える PARTIAL が 2 回ありました（L4 #2、#5）。
- 第 1 回は範囲外や重複のエラーが中心でしたが、第 2 回は書式エラーが増えました。

### 4. ガイドを増やしても、すぐには改善しない
レベル 1 と 2 の PASS が少し増えたのは、ばらつきの範囲内だと考えています（試行回数が少ないため）。
レベル 3〜5 は改善しませんでした。ガイドの記載を増やすだけでは、このモデルの空間的な推論の弱さは補えません。下の「改善の方向」にある、Python 側で座標を計算する方法を試す価値が高いと考えます。

## 改善の方向（案）

- **モデルに文法を丸ごと書かせない**：「公園」「大路」「水路」などの要素を `@fm.generable` の構造化出力で受け取り、範囲のクリップや交差の回避は Python 側で計算する
- **ツールを細かく分ける**：「公園を置く」「大路を引く」など、要素ごとのツールに分けて、1 回の呼び出しで決めることを減らす
- **エラーの返し方を工夫する**：tinytowngen のエラーをそのまま返すのではなく、修正案（例：「`F{1,3-11}` にすると公園を避けられます」）を Python 側で計算して返す
- **クラウドモデル（PCC）で比べる**：より大きなモデルでどこまで改善するかを比べる（[private-cloud-compute.md](private-cloud-compute.md) の通り、今の環境では使えません）

## 再実行の方法

```bash
source .venv/bin/activate
python tinytown_eval.py             # 全レベル × 3 回
python tinytown_eval.py -l 4 -n 5   # レベル 4 だけ 5 回
```

- 試行ごとの詳細（エラーメッセージ、最終的なレイアウト、モデルの応答）は `output/eval/results.json` に保存されます。実行するたびに上書きされるので、残したい結果は別の名前に変えておいてください（第 1 回の結果は `results_v1.json` に退避済み）。
- 成功した回の画像は `output/eval/L{レベル}_t{試行}_c{呼び出し番号}.png` という名前で保存されます。
- モデルの出力は毎回変わるため、結果は実行ごとにばらつきます。
